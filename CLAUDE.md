# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Code Review Workflow
Before running code reviews, verify there is a pending diff (`git diff` or `git status`) and that the `gh` CLI is installed (`gh --version`). If either is missing, prompt the user for how to proceed rather than failing.

## Project

PTime ("Project time keeping, the easy way") is a German-language Android app for tracking time bookings against projects (start/stop a timer, review daily/weekly/monthly/yearly summaries, export/import CSV). All UI strings, comments, and commit history are predominantly German.

## Build

There is no unit/instrumentation test setup in this repo (no `test`/`androidTest` source sets, no test runner configured). The only "test" file, `project4/.../test/ProjectTypeComparatorTest.java`, is a plain class under `src/main` with its body fully commented out — it does not run as part of any build task. Do not assume `./gradlew test` exercises anything meaningful.

## Module structure

Note: the app currently only builds as a single "Free" variant (package suffix `.free`, `AppType.FREE`). `Project4App.isPro()` / `AppType.PRO` exist in the code but there is no `pro`-flavored application module wired up in `settings.gradle` right now.

## Architecture

**Application/DI bootstrap** (`project4/.../app/Project4App.java`, extended by `pTime`'s `PTimeApp`): on `onCreate()` it opens the greenDAO SQLite database (`project4-db`) via `SelectiveUpdateOpenHelper`, constructs `ProjectDao`/`BookingDao` and the corresponding `ProjectService`/`BookingService`, and builds a Dagger `ServiceComponent` (currently only used to inject `BookingImportService` into `ExportImporter`) — Dagger is a single injection point here, not a full DI architecture; don't assume other classes are container-managed. `Project4App` also holds a lot of screen-to-screen transient state as plain fields (e.g. `editProjectColorString`, `editBooking`, `lastBookingList`, `importList`, the in-memory `Summary`) — activities read/write this state directly via `Project4App.getApp(context)` rather than passing it through intents or a shared ViewModel. Keep this pattern in mind when tracing how data flows between activities.

**Persistence**: greenDAO 1.x (old `de.greenrobot.dao` package, not the newer `org.greenrobot`). `DaoMaster`/`DaoSession`/`*Dao`/entities (`Booking`, `Project`) under `project4/.../dao` and `.../entity` are **generated code** — files carry `// THIS CODE IS GENERATED BY greenDAO, EDIT ONLY INSIDE THE "KEEP"-SECTIONS` and have `KEEP INCLUDES`/`KEEP FIELDS`/`KEEP METHODS` markers; only edit inside those markers. Schema migrations are hand-written (not greenDAO-generated) in `SelectiveUpdateOpenHelper` as numbered `migrateToN(db)` static methods per table (`BookingTable`, `ProjectTable`) — when changing an entity's persisted fields, add a new `migrateToN` step here and bump the DB version rather than relying on greenDAO's own `DevOpenHelper` upgrade path.

**Service layer** (`project4/.../service`): `ProjectService`, `BookingService`, `ProjectCardService`, `BookingImportService` wrap DAO queries with domain logic (e.g. `BookingService` builds green DAO `QueryBuilder`/`DeleteQuery` for period-based lookups — today/week/month/year/prior month/prior year — and implements the start/stop-timer logic including splitting a booking that spans midnight into multiple per-day bookings in `bookStop`/`splitStopBooking`).

**Summary/reporting**: `Summary.java` is an in-memory aggregate (not persisted) rebuilt from the booking list (`loadNew`) that tracks running totals per day/week/month and per-project maps (`projectsToday`/`projectsWeek`/`projectsMonth` → `BookedValues`). `PeriodType` enum drives which date range a query/report uses (`TODAY`, `WEEK`, `MONTH`, `YEAR`, `PRIOR_YEAR`, `PRIOR_MONTH`, `SELECT_MONTH`). Note that `Summary`'s own day/week/month bucketing (`isDay`/`isWeek`/`isMonth`) is a second, independent implementation of the same "which period does this date fall into" logic that `BookingService`'s `getToday`/`getThisWeek`/etc. already implement via SQL — the two aren't derived from each other, so a period-boundary fix (e.g. week start day) needs to be applied in both places.

**UI layer**: mostly classic `Activity`/`Fragment` + `ArrayAdapter` (`project4/.../activity`, `.../fragment`, `.../listadapter`), with dialogs built via a small `dialogcontroller` package (`DefaultDialogController`, `ColorPickerDialogController`, `ProjectSelectionDialogController`, `PeriodSummaryDialogController`). One screen (`BackupRestoreActivity`) uses an MVC split (`mvc/controller/ControllerMvc`, `mvc/view/ViewMvc` + impl) — this is the exception, not the norm; don't assume other activities follow it. The stack predates AndroidX and Jetpack Compose (dependencies are `com.android.support:*`, not `androidx.*`) — there's no ViewModel/LiveData layer, so don't reach for those APIs when extending a screen.

**CSV export/import**: `async/ExportGenerator`, `async/ExportImporter` (Dagger-injected), `async/ImportResult` handle writing/reading booking CSVs, invoked from `BackupRestoreActivity`/`BookingImportActivity`.

## Conventions to follow

- Match the existing mixed indentation (tabs in most `project4` classes, spaces in generated DAO/entity files) within whatever file you're editing rather than reformatting.
- Logging goes through `com.gek.and.project4.util.L.d(tag, message)`, which is a no-op unless a debugger is attached (`android.os.Debug.isDebuggerConnected()`) — not gated by build type.
- Don't touch generated greenDAO files (`dao/`, `entity/`) outside the `KEEP` markers; add schema changes via a new `migrateToN` step in `SelectiveUpdateOpenHelper` instead.
